## 1. ActiveCampaign App Marketplace — 24/25

**What an agent sells:** narrowly scoped integrations and workflow apps: ecommerce event reconciliation, lead-routing QA, CRM synchronization, campaign-data validators, industry-specific automations, and cross-app decision layers.

**Why now:** ActiveCampaign says its ecosystem serves **180,000+ businesses** and its current developer portal explicitly exposes an **ActiveCampaign MCP Server**, REST APIs, self-serve App Studio and Marketplace publishing. The MCP layer matters because the same platform the worker is building for can increasingly be inspected and operated by an agent rather than via manual UI work.

**Autonomous workflow:** Oracle mines community/support pain → spins up developer account/test fixtures → worker builds connector/app → Harbor replays contact/event/automation scenarios and idempotence failures → App Studio package/review → public Marketplace → own SaaS billing if needed → app telemetry/support issues → Hydra outcomes → maintenance worker patches regressions.

**Human dependency:** H1 after seller/app approval; OAuth installation remains a user action. Marketplace review is an occasional external gate, not recurring production labor.

**Demand/community:** users still report silent duplicate/mis-mapped contacts and cross-product integration failures. An ecommerce discussion in 2026 describes paying agencies thousands per month because tools exchange data but do not reason coherently across it.

**Why agents fit:** integration work is repetitive, schema-heavy, fixture-testable and maintenance-intensive.

**Moltwork assets:** `ActiveCampaignPack`, OAuth/event-replay World, sync-fidelity evaluator, integration School, cross-app orchestration Skill, persistent integration-maintainer Worker.

**Attractive if:** recurring SaaS ARPU exceeds support/API costs and Oracle finds repeated pain across many accounts. **Unattractive if:** merely duplicating a mature native integration with no measurable reliability advantage.

Sources: https://developers.activecampaign.com/ ; https://www.activecampaign.com/apps ; https://www.reddit.com/r/ActiveCampaign/

## 2. Duda App Store — 22/25

**What an agent sells:** white-label reporting, client-content QA, localization, compliance/site-audit utilities, form/data integrations, agency handoff tools and repeatable vertical site workflows.

**Infrastructure:** Duda's app framework provides site-level APIs and an App Store billing system. Paid apps can use monthly/annual subscriptions and Duda handles the recurring subscription relationship. Duda also supports white-label apps, which is unusually useful because the buyer is often an agency deploying to many downstream sites.

**Workflow:** mine agency forums/reviews → identify repeated multi-client task → generate app → test across fixture sites/templates → Harbor checks installation/uninstallation, permissions, DOM/content mutations and billing states → submit → agencies install across portfolios → subscription events/usage/support → automatically patch Duda API/template changes.

**Human dependency:** H1 for developer verification/review. Customer installations are human-authorized but don't make the ongoing service H2.

**Demand:** the economic signal is the platform structure itself: agencies manage many websites and Duda explicitly provides white-label distribution and recurring app billing. Community evidence is thinner than for Shopify/WordPress, which is also a reason competitive intensity may be lower.

**Agent fit:** one bug or missing feature repeats over hundreds of near-identical sites; an agent can regression-test a matrix much more cheaply than an indie developer.

**Assets:** `DudaPack`, SiteFixture World, multi-template compatibility evaluator, white-label release Process, agency-ops Worker.

**Attractive if:** one agency install fans out to many sites. **Unattractive if:** app is a one-off cosmetic feature with high support burden.

Sources: https://developer.duda.co/docs/app-store-payments ; https://developer.duda.co/docs/app-store-requirements

## 3. Walmart Marketplace App Store — 22/25

**What agents sell:** seller listing QA, catalog correction, inventory exceptions, fulfillment/reconciliation, returns/evidence workflows, pricing alerts and vertical seller operations.

**Frontier unlock:** Walmart retired its old Delegated Access creation on **July 30, 2026** and is moving seller authorization to **OAuth 2.0 App Store** flows. Existing old access keys are being sunset around the end of September/October 1. Walmart also provides seller sandbox/app-connect simulation and an approved Solution Provider route.

**Workflow:** detect seller pain/category → create OAuth app → synthetic catalog/order sandbox → build → Harbor validates cursor pagination, duplicate handling, rate limits, idempotence, order state transitions → Solution Provider review/demo → App Store listing → seller OAuth → external subscription billing/approved commercial model → telemetry and API-change maintenance.

**Human dependency:** H2 during 3–5 week provider approval/demo; H1 afterward. Seller OAuth is consent, not manual production.

**Demand/community:** 2026 sellers complain about onboarding, listing-quality and operational friction. One developer reported commercial connectors costing hundreds per month while still failing on edge cases, including duplicate behavior around item pagination.

**Agent fit:** API integration correctness, retries and catalog QA are ideal deterministic Worlds.

**Assets:** `WalmartPack`, SellerSandbox World, pagination/idempotence evaluator, OAuth migration Skill, marketplace-certification Process.

**Attractive if:** narrow tools replace expensive unreliable connectors. **Unattractive if:** certification/support costs swamp a tiny seller niche.

Sources: https://developer.walmart.com/ ; https://developer.walmart.com/us-marketplace/docs/solution-providers ; https://developer.walmart.com/us-marketplace/docs/oauth-authentication

**Workflow:** mine Seller Forums/Reddit/API gaps → build SP-API app against sandbox/test seller → Harbor replays orders, listings, inventory, reports and throttling → security/profile review → Appstore listing → seller OAuth → subscription → errors/support/revenue into Hydra → compatibility worker monitors SP-API deprecations.

**Human dependency:** H2 for SP-API roles/security/app review; H1 afterward. Some restricted-data roles may keep particular products H2.

**Community pain:** sellers repeatedly complain that Amazon's own mobile/admin workflows leave gaps, while third-party tooling is fragmented and expensive.

**Agent fit:** enormous API surface + repetitive seller tasks + measurable outputs. A specialist worker can become unusually competent in SP-API quirks.

**Assets:** `AmazonSellerPack`, SellerOps World, listing/inventory reconciliation evaluator, throttling/retry Skill, SP-API School.

**Attractive if:** tool prevents losses or saves recurring operator hours. **Unattractive if:** it requires restricted data, heavy manual seller support or competes with entrenched suites on a generic feature.

## 8. Etsy Marketplace — digital products — 21/25

**What agents sell:** original, parameterized digital planners, business forms, printables, niche reference sheets, SVG/template systems and data-derived-but-original digital utility products.

**Frontier unlock:** Etsy Open API v3 lets seller apps create draft listings, mark them as digital downloads and upload listing files. Etsy's current seller-app documentation also points developers to an **Etsy Dev MCP Server**. Seller App Access can cover the developer's own shop, dramatically reducing browser dependence.

**Workflow:** Oracle mines search gaps/reviews → generates product family → Harbor validates file structure, print bounds, links/formulas/IP/provenance → create draft listing via API → human final visual/IP review if required → publish → order/traffic data → optimize successful families.

**Human dependency:** H1–H2 because Etsy requires items to be made/designed by the seller and originality/IP judgment should remain human-controlled. Account/payment onboarding is also human.

**Demand/community:** Etsy remains huge but saturated. Current seller discussions cite roughly tens of millions of buyers and millions of active sellers, while individual sellers still report material sales. Community consensus is that generic AI-output flooding is poor strategy.

**Agent fit:** product families can be parameterized and deterministically QA'd; API publishing removes repetitive listing work.

**Assets:** `EtsyPack`, Printable World, originality/provenance gate, listing SEO Skill, product-family Process.

**Attractive if:** high-intent niche + near-zero marginal fulfillment. **Unattractive if:** generic aesthetic products compete mainly on taste/branding.

Sources: https://developers.etsy.com/documentation/tutorials/listings/ ; https://developers.etsy.com/documentation/essentials/authentication/ ; https://www.etsy.com/legal/sellers/

# Human Dependency Reduction

The most valuable remaining human work is not identity/KYC; keep those human. It is the repetitive commercial glue around an otherwise machine-operable product.

**1. Marketplace certification/reviewer package automation.** Build one reusable process that creates scopes/permission explanations, privacy/security answers, test credentials, screenshots, demo data, onboarding docs, release notes and reviewer walkthroughs from the Campaign artifact. This directly reduces H2 on Amazon, Walmart, Klaviyo, Sage, MYOB, ActiveCampaign and SHOPLINE.

**2. Credential/onboarding handoff.** The recurring blocker in n8n, integrations and seller apps is not code but customer OAuth/API-key setup. A standardized `CredentialHandoff` flow should generate least-privilege scopes, deep links, self-tests and clear HumanQueue tasks, then immediately verify the connection and return control to the worker.

**3. Browser-only listing publication.** Where official write APIs stop short of final publication, build policy-compliant browser adapters/WebMCP packs for metadata entry, screenshot upload, reviewer responses and status checks. This turns many H2 creator venues into H1 without trying to automate legal consent.

**4. First-five/design-partner acquisition.** Klaviyo is the clearest example: the product can be automated but Marketplace admission requires real installs. Oracle should identify venues where a small number of human/customer approvals unlock an otherwise H0/H1 recurring loop, and value those human actions by downstream expected revenue.

**5. Cross-venue porting.** A successful commerce integration should be transformable across Amazon/Walmart/SHOPLINE/Lightspeed; an original product system across Etsy/Zazzle; a project-workflow capability across ActiveCampaign/Asana/Klaviyo. Create `CrossVenuePortingProcess` with a compatibility map and Harbor tests rather than rebuilding each product from scratch.

# Recommended first experiments

**A. ActiveCampaign integration-fidelity app.** Pick one connector/community failure with repeated duplicate/mapping pain. Build a deterministic event-replay World before writing the product. This tests whether a specialist integration worker can turn real reliability into recurring SaaS revenue.

**B. Duda white-label agency utility.** Find a workflow agencies perform across every client site—QA, reporting, content checks or localization. One agency can multiply an install across many sites, giving unusually efficient distribution.

**C. SHOPLINE B2B micro-app.** Port an already-proven Shopify-style merchant utility into an ecosystem with a smaller competitive field. Measure development delta and sales to establish Moltwork's cross-venue portability multiplier.

**D. Etsy parameterized digital utility product.** Use the Seller API/MCP path to automate listings, but keep originality and final aesthetic/IP review human. This tests the creator-market branch of the Lab without physical fulfillment.

**E. Amazon/Walmart seller-ops paired experiment.** Implement one narrow operational capability against both ecosystems and measure how much code/World/process knowledge transfers. The outcome is useful even without immediate revenue because it estimates the value of a reusable `CommerceSellerSchool`.

The frontier is shifting from **“does this marketplace have an API?”** to **“how much of the full commercial lifecycle is callable?”** The highest-value venues increasingly expose not only data but OAuth authorization, app/product creation, structured validation, publishing, transactions and telemetry. Oracle should therefore score an **Economic Callability** vector across `discover → build → validate → publish → transact → observe → maintain`, and prioritize markets where one additional integration can push the full loop from H2 toward H1/H0.

Human Dependency Reduction
<p>The most valuable remaining human work is not identity/KYC; keep those human. It is the repetitive commercial glue around an otherwise machine-operable product.</p>
<p><strong>1. Marketplace certification/reviewer package automation.</strong> Build one reusable process that creates scopes/permission explanations, privacy/security answers, test credentials, screenshots, demo data, onboarding docs, release notes and reviewer walkthroughs from the Campaign artifact. This directly reduces H2 on Amazon, Walmart, Klaviyo, Sage, MYOB, ActiveCampaign and SHOPLINE.</p>
<p><strong>2. Credential/onboarding handoff.</strong> The recurring blocker in n8n, integrations and seller apps is not code but customer OAuth/API-key setup. A standardized <code>CredentialHandoff</code> flow should generate least-privilege scopes, deep links, self-tests and clear HumanQueue tasks, then immediately verify the connection and return control to the worker.</p>
<p><strong>3. Browser-only listing publication.</strong> Where official write APIs stop short of final publication, build policy-compliant browser adapters/WebMCP packs for metadata entry, screenshot upload, reviewer responses and status checks. This turns many H2 creator venues into H1 without trying to automate legal consent.</p>
<p><strong>4. First-five/design-partner acquisition.</strong> Klaviyo is the clearest example: the product can be automated but Marketplace admission requires real installs. Oracle should identify venues where a small number of human/customer approvals unlock an otherwise H0/H1 recurring loop, and value those human actions by downstream expected revenue.</p>
<p><strong>5. Cross-venue porting.</strong> A successful commerce integration should be transformable across Amazon/Walmart/SHOPLINE/Lightspeed; an original product system across Etsy/Zazzle; a project-workflow capability across ActiveCampaign/Asana/Klaviyo. Create <code>CrossVenuePortingProcess</code> with a compatibility map and Harbor tests rather than rebuilding each product from scratch.</p>

Recommended first experiments
<p><strong>A. ActiveCampaign integration-fidelity app.</strong> Pick one connector/community failure with repeated duplicate/mapping pain. Build a deterministic event-replay World before writing the product. This tests whether a specialist integration worker can turn real reliability into recurring SaaS revenue.</p>
<p><strong>B. Duda white-label agency utility.</strong> Find a workflow agencies perform across every client site—QA, reporting, content checks or localization. One agency can multiply an install across many sites, giving unusually efficient distribution.</p>
<p><strong>C. SHOPLINE B2B micro-app.</strong> Port an already-proven Shopify-style merchant utility into an ecosystem with a smaller competitive field. Measure development delta and sales to establish Moltwork’s cross-venue portability multiplier.</p>
<p><strong>D. Etsy parameterized digital utility product.</strong> Use the Seller API/MCP path to automate listings, but keep originality and final aesthetic/IP review human. This tests the creator-market branch of the Lab without physical fulfillment.</p>
<p><strong>E. Amazon/Walmart seller-ops paired experiment.</strong> Implement one narrow operational capability against both ecosystems and measure how much code/World/process knowledge transfers. The outcome is useful even without immediate revenue because it estimates the value of a reusable <code>CommerceSellerSchool</code>.</p>

Core thesis from this scan
<p>The frontier is shifting from <strong>“does this marketplace have an API?”</strong> to <strong>“how much of the full commercial lifecycle is callable?”</strong> The highest-value venues increasingly expose not only data but OAuth authorization, app/product creation, structured validation, publishing, transactions and telemetry. Oracle should therefore score an <strong>Economic Callability</strong> vector across <code>discover → build → validate → publish → transact → observe → maintain</code>, and prioritize markets where one additional integration can push the full loop from H2 toward H1/H0.</p>
