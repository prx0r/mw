## 1. Square App Marketplace — 24/25

**What an agent can sell:** merchant-facing SaaS for catalog QA, loyalty automation, restaurant ops, inventory alerts, appointment workflows, vertical reporting, shipping, staff workflows, reconciliation helpers, and narrow AI assistants.

**Why now:** Square has public APIs, sandbox, OAuth, webhooks, a self-serve App Marketplace submission flow, App Subscriptions for charging sellers through Square, and an official Square MCP server. A 2026 public platform retrospective states that Square’s APIs process more than $18B annual GPV and that 71% of enterprise sellers use a partner solution, indicating real distribution rather than a decorative directory.

**Autonomous loop:** Oracle mines seller/community pain → worker scaffolds app → Square Sandbox merchant fixture → Harbor replays orders/catalog/customers/webhooks → OAuth/security preflight → self-serve Marketplace submission → App Subscription billing → usage/error telemetry → agent patches against API changes.

**Human dependency:** H1 for seller identity, production OAuth approval, policy/review; ongoing provisioning, service delivery, updates and billing can approach H0.

**Community signal:** Square’s partner ecosystem is large and merchants commonly stack third-party apps; the challenge is distribution and vertical specificity, not whether integrations are used.

**Moltwork assets:** `SquarePack`, merchant World, webhook/idempotence evaluator, billing lifecycle World, OAuth Scope Skill, MarketplaceSubmissionProcess, persistent POS specialist Worker.

**Economically good when:** measurable recurring merchant pain, low-support integration, vertical-specific ROI. **Bad when:** generic analytics, saturated accounting sync, or human support dominates ARR.

Official developer platform: https://developer.squareup.com/
Marketplace: https://squareup.com/us/en/app-marketplace

## 2. Heroku Add-ons Marketplace — 24/25

**What agents sell:** databases/caches, log processors, testing services, monitoring, API utilities, security scanners, data transforms, scheduled jobs, webhook infrastructure, specialist agent services.

**Frontier unlock:** Heroku now has an official MCP Server. Current tooling exposes app creation/deployment, dyno control, logs, pipelines, Postgres operations, and **add-on provisioning** directly to MCP-capable agents. That means the worker building/testing a commercial add-on can also create disposable Heroku worlds and provision dependencies without dashboard work.

**Workflow:** identify recurrent developer pain → build metered service + add-on manifest → create disposable Heroku apps via MCP/CLI → integration and failure-injection World → provider review → Marketplace distribution/native Heroku billing → observe usage/SLOs → autonomous release/capacity maintenance.

**Human dependency:** H1–H2 for provider agreement/company/payment/security review; normal operations can be H0.

**Agent fit:** exceptional. The product is an API/service and the test surface is machines all the way down.

**Moltwork:** `HerokuAddonPack`, provisioning World, SLO/cost evaluator, failure-recovery World, metered-pricing Process, infra-specialist School.

**Good when:** low marginal cost and clear per-app value. **Bad when:** high 24/7 support burden or cloud costs erase margin.

Heroku MCP: https://github.com/heroku/heroku-mcp-server
Heroku Elements/Add-ons: https://elements.heroku.com/addons

## 3. Clover App Market — 23/25

**What agents sell:** restaurant/retail POS utilities, scheduling, staff tools, menu QA, inventory alerts, local compliance workflows, order routing, accounting/export helpers, loyalty and vertical reporting.

**Economics:** Clover’s App Market supports paid merchant apps; current partner-program summaries cite developers receiving roughly 70% of app subscription revenue. Clover exposes REST APIs/SDKs around merchants, orders, inventory, employees and payments.

**Workflow:** mine restaurant/retail pain → create sandbox merchant + sample catalog → build app → replay shifts/orders/refunds/offline edge cases → security/device preflight → App Market review → recurring app subscriptions → monitor merchant events/support → patch.

**H-level:** H1–H2 at production/payment/review; H1 ongoing.

**Demand:** strong because the buyer already lives inside a POS and pays for business software; easier monetization than convincing a random consumer to buy another SaaS.

**Moltwork:** CloverPack, POS World, shift/order invariant evaluator, hardware compatibility matrix, merchant onboarding Skill.

**Bad economics:** features Clover is likely to absorb into core, high hardware-support burden, tiny merchants with high churn.

Marketplace: https://www.clover.com/appmarket
Developer docs: https://docs.clover.com/

## 4. Odoo Apps Store — 23/25

**What agents sell:** ERP modules for country/local tax workflows, vertical manufacturing, import/export, CRM micro-features, document generation, data QA, niche marketplace connectors, migration helpers and Odoo 19/20 compatibility.

**Why agent-suited:** Odoo modules are structured Python/XML packages and the ERP surface can be reproduced with fixture companies, invoices, inventory, purchase orders and manufacturing flows. Odoo’s annual major-release cadence creates continuous paid compatibility labor.

**Workflow:** mine Odoo forum/App Store gaps → scaffold module → disposable Odoo DB → deterministic business-flow World → package/version → listing/review → observe support/reviews → automatically test against next Odoo release and port.

**H-level:** H1 marketplace/payment/account setup; code/testing/maintenance can be H0-ish.

**Demand:** Odoo is reported at 16M+ users globally in 2026; even without trusting that exact third-party number, the paid Apps Store has a mature worldwide ecosystem and many $20–$500+ modules.

**Community intel:** Odoo communities repeatedly revolve around missing vertical workflows and version migration. Oracle should prioritize gaps tied to local regulation or obscure integrations, not generic CRM widgets.

**Moltwork:** OdooPack, ERP World, accounting/inventory evaluator, migration School, version-matrix Process.

Store: https://apps.odoo.com/

## 5. Craft CMS Plugin Store — 23/25

**What agents sell:** commercial plugins for content workflows, SEO/data QA, integrations, forms, ecommerce operations, developer tooling and AI/content governance.

**Hard economics:** Craft’s current terms explicitly allow developers to sell plugins; Craft deducts **20%**, handles transaction fees/tax, and generally pays developers through linked Stripe. Commercial plugins use Craft’s licensing system and must live in a public GitHub repo.

**Workflow:** detect missing professional CMS capability → generate/scaffold Composer plugin → DDEV fixtures across Craft versions → Harbor install/update/uninstall + security + content-state tests → public GitHub → Plugin Store submission → sales/license telemetry → version maintenance.

**H-level:** H1. Seller/Stripe/review is human; almost everything else can automate.

**Why attractive:** buyers expect to pay for reliable, maintained plugins; local dev trials are free, making automated QA easy. Commercial support and compatibility are part of the value proposition.

**Moltwork:** CraftPack, CMS fixture World, migration/security evaluator, Composer release Skill, plugin-maintainer Worker.

Official terms: https://craftcms.com/terms-of-service

## 6. Concrete CMS Marketplace — 22/25

**What agents sell:** search, A/B testing, recommendation, workflow, ecommerce integration, AI governance, content operations and headless tooling add-ons.

**Why now:** Concrete 9.5.x has continued active 2026 releases. A current independent platform audit finds the Marketplace still active with 2026 additions and identifies obvious capability gaps: no native A/B testing, weak advanced search, no recommendation engine and little agentic automation. More interestingly, there is now a community `concretecms-mcp-server` built over Concrete’s REST/OpenAPI surface with content read/write and file-upload capabilities.

**Workflow:** Oracle turns an explicit capability gap into a package → fixture Concrete instance → tests installs/content mutations/permissions → Marketplace listing → monitor installs/reviews → patch against core releases.

**H-level:** H1.

**Community signal:** smaller than WordPress, which is a feature here: less competition, but smaller TAM. Marketplace pricing can be meaningful because buyers are business/government sites.

**Moltwork:** ConcretePack, CMS World, OpenAPI/MCP adapter, role/permission evaluator, package boilerplate Skill.

Marketplace: https://market.concretecms.com/

## 7. WHMCS Marketplace — 22/25

**What agents sell:** hosting/billing modules, client-area utilities, provisioning adapters, domain/registrar integrations, invoicing tools, notifications, support automation and admin workflows.

**Demand evidence:** the live Marketplace contains paid modules with current 2026 reviews; one small `Client Notifications` module is $29.99 and has 60+ five-star reviews, while many integration/automation modules sell for materially more.

**Workflow:** mine hosting-company complaints → generate module → fixture WHMCS install with fake products/clients/invoices → lifecycle tests → Marketplace listing → license/payment path → monitor WHMCS releases/support → patch.

**H-level:** H1.

**Why agents fit:** PHP modules have deterministic hooks/API contracts, and hosting businesses will pay to remove repetitive operations. Persistent maintenance is more important than clever generation.

**Moltwork:** WHMCSPack, billing/provisioning World, invoice evaluator, upgrade matrix, hosting-specialist Worker.

## 8. CS-Cart Marketplace — 22/25

**What agents sell:** ecommerce/multi-vendor integrations, feed import/export, logistics, payment gateways, accounting connectors, vendor tooling and compliance modules.

**Current market evidence:** the Marketplace is active in 2026. Current listings include an Amazon Connector at $159, import/export products from $25 to hundreds of dollars, and a Site Management category with hundreds of add-ons. A current marketplace page shows 858 Site Management items and 92 Import/Export products — real depth but still much smaller than Shopify.

**H-level:** H1.

**Community:** official CS-Cart forums repeatedly emphasize post-sale support and compatibility; that favors persistent worker ownership.

**Moltwork:** CSCartPack, multi-vendor World, catalog/order-sync evaluator, external-API change monitor.

## 11. WeChat Mini Programs — 21/25

**What agents sell:** not source-code listings but actual paid service micro-apps inside WeChat: business utilities, booking/order helpers, merchant/customer workflows, vertical calculators, local tools and lightweight SaaS.

**Infrastructure:** WeChat Mini Programs have rich APIs, official developer tools and native WeChat Pay. Tencent CloudBase now has an Integration Center that can automatically generate the Mini Program payment cloud-function layer for order creation, query, refund and callback verification. `wx.cloud.callHTTPFunction` handles app identity injection.

**Autonomous workflow:** discover Chinese SMB niche → Taro/uni-app scaffold → agent builds → simulator/real-device compatibility World → CloudBase + WeChat Pay integration → generate review/privacy materials → human merchant verification/review → publish → transaction telemetry → update.

**H-level:** H2 because verified Mini Program + merchant/payment admin steps require humans; ongoing product and operations can be H1.

**Demand evidence:** public ecosystem sources cite 600M+ daily active Mini Program users and 10M+ developers. Treat those numbers as directional, but the market scale is unquestionably enormous.

**Moltwork:** WeChatPack, MiniProgram World, payment-callback evaluator, review-material Process, Chinese vertical School.

CloudBase payment guide: https://docs.cloudbase.net/en/integration/wechat-pay-miniprogram

## 12. Alipay Mini Programs — 21/25

**What agents sell:** merchant/service mini-apps centered on transactions, local services, finance-adjacent business operations, memberships, bookings and commerce utilities.

**Infrastructure:** Alipay Mini Programs have an official IDE/runtime, native payment capability and comprehensive APIs. They can also use Alibaba EMAS Serverless SDKs. Cross-platform frameworks such as Taro/uni-app let the same core code compile for WeChat + Alipay, radically lowering marginal cost for a second market.

**H-level:** H2 merchant/account/payment review; H1 operations.

**Strategic insight:** the product may not be one Alipay app; the Moltwork asset is a **MiniProgramPortingProcess** that turns one successful service into WeChat/Alipay/Douyin/Baidu variants.

# Frontier Unlocks

### 1. Square MCP turns merchant-app development into an agent-operable loop
Square’s MCP/API ecosystem means agents can increasingly inspect/manage seller resources while building against the same platform. Pair that with App Subscriptions and self-serve App Marketplace submission and the economic lifecycle becomes unusually callable.

### 2. Heroku MCP is a major development-speed unlock
Heroku’s official MCP server can create/deploy apps, inspect logs, scale processes, manage Postgres and provision add-ons. That means a Moltwork worker can create its **own disposable evaluation infrastructure**, dramatically reducing H-level for add-on development.

### 3. Concrete CMS now has an OpenAPI→MCP path
A community MCP server wraps Concrete’s REST API/OpenAPI definition for content read/write/file operations. Even though it is not official, it shows a reusable pattern: Oracle discovers a marketplace with OpenAPI → Moltwork auto-generates an MCP adapter → the worker gains direct control of the test world.

### 4. WeChat CloudBase has compressed the payment integration surface
CloudBase Integration Center now encapsulates Mini Program order creation, query, refunds and callback verification in generated cloud functions. The remaining hard work is merchant identity/review, not basic payment plumbing.

### 5. Taro/uni-app make mini-program market expansion compositional
A successful WeChat mini-app can be ported by mapping `wx.*` → `my.*` and handling platform review differences rather than rewritten from scratch. Oracle should score **cross-market portability** as a major multiplier.

# Human Dependency Reduction

The highest-value human dependencies to automate next are not KYC or legal acceptance. Leave those human. The money is in reducing repeated operational H1/H2 steps:

1. **Marketplace submission compiler** — Given a finished product and Venue schema, generate screenshots, demo data, listing copy, permissions/OAuth justification, privacy text, support URL, release notes, compatibility table and reviewer test instructions.

2. **Review/rejection loop** — Parse Marketplace rejection → map it to a requirement/evaluator → patch code/listing → rerun Harbor → resubmit. This can turn mandatory human review from an iterative bottleneck into a one-click approval checkpoint.

3. **Version-matrix maintenance** — Odoo/Craft/Concrete/WHMCS/CS-Cart/Statamic/October all reward continuous upstream-release testing. Build one general `CompatibilitySchool` that watches new versions and runs every owned product before users complain.

4. **Merchant fixture factories** — Square/Clover/WeChat/Alipay Worlds should be generated from canonical synthetic businesses: restaurant, salon, ecommerce store, service contractor, agency. This makes many future products testable with the same Harbor substrate.

5. **OpenAPI/MCP adapter factory** — When Oracle discovers an official OpenAPI/CLI, automatically generate or install an agent-facing interface and update the opportunity’s H-level. Concrete shows the pattern; Heroku/Square show the end state.

6. **Artifact-family expansion** — Once one product sells, the worker should create adjacent variants only after outcome evidence: one Odoo localization → related compliance module; one technical 3D object → parametric family; one mini-app → cross-platform port. This is where persistent worker knowledge should compound.

# Recommended experiments

**1. Square micro-app:** find one narrow merchant pain with a measurable $ value and build the full Sandbox → Harbor → App Subscription path.

**2. Heroku add-on:** build a tiny developer service with metered economics and use Heroku MCP to have the worker create its own integration-test worlds.

**3. Craft commercial plugin:** smallest clean experiment in true plugin-market revenue. Craft’s 20% commission, GitHub requirement and licensing system make outcomes easy to attribute.

**4. Odoo vertical module:** test the persistent-maintainer thesis across annual ERP versions and one region/industry niche.

**5. WeChat→Alipay paired experiment:** build one extremely narrow paid utility, then measure the marginal labor/cost to port it to the second mini-program ecosystem. This directly tests whether `CrossVenuePortingProcess` becomes a reusable Moltwork asset.

## Core Oracle conclusion

This batch reinforces a useful filter: the best market is not necessarily the biggest marketplace. It is the market where **economic callability × repeatable evaluation × recurring maintenance value** is highest.

Square and Heroku lead this run because the product, test environment, operations and billing are increasingly machine-operable. Craft/Odoo/CMS stores are attractive because the artifacts are deterministic and buyers pay for maintenance. Mini Programs are strategically huge because a successful worker/process may transfer across multiple super-app ecosystems.

Frontier Unlocks

1. Square MCP turns merchant-app development into an agent-operable loop
<p>Square’s MCP/API ecosystem means agents can increasingly inspect/manage seller resources while building against the same platform. Pair that with App Subscriptions and self-serve App Marketplace submission and the economic lifecycle becomes unusually callable.</p>

2. Heroku MCP is a major development-speed unlock
<p>Heroku’s official MCP server can create/deploy apps, inspect logs, scale processes, manage Postgres and provision add-ons. That means a Moltwork worker can create its <strong>own disposable evaluation infrastructure</strong>, dramatically reducing H-level for add-on development.</p>

3. Concrete CMS now has an OpenAPI→MCP path
<p>A community MCP server wraps Concrete’s REST API/OpenAPI definition for content read/write/file operations. Even though it is not official, it shows a reusable pattern: Oracle discovers a marketplace with OpenAPI → Moltwork auto-generates an MCP adapter → the worker gains direct control of the test world.</p>

4. WeChat CloudBase has compressed the payment integration surface
<p>CloudBase Integration Center now encapsulates Mini Program order creation, query, refunds and callback verification in generated cloud functions. The remaining hard work is merchant identity/review, not basic payment plumbing.</p>

5. Taro/uni-app make mini-program market expansion compositional
<p>A successful WeChat mini-app can be ported by mapping <code>wx.*</code> → <code>my.*</code> and handling platform review differences rather than rewritten from scratch. Oracle should score <strong>cross-market portability</strong> as a major multiplier.</p>



Human Dependency Reduction
<p>The highest-value human dependencies to automate next are not KYC or legal acceptance. Leave those human. The money is in reducing repeated operational H1/H2 steps:</p>
<ol>
<li>
<p><strong>Marketplace submission compiler</strong> — Given a finished product and Venue schema, generate screenshots, demo data, listing copy, permissions/OAuth justification, privacy text, support URL, release notes, compatibility table and reviewer test instructions.</p>
</li>
<li>
<p><strong>Review/rejection loop</strong> — Parse Marketplace rejection → map it to a requirement/evaluator → patch code/listing → rerun Harbor → resubmit. This can turn mandatory human review from an iterative bottleneck into a one-click approval checkpoint.</p>
</li>
<li>
<p><strong>Version-matrix maintenance</strong> — Odoo/Craft/Concrete/WHMCS/CS-Cart/Statamic/October all reward continuous upstream-release testing. Build one general <code>CompatibilitySchool</code> that watches new versions and runs every owned product before users complain.</p>
</li>
<li>
<p><strong>Merchant fixture factories</strong> — Square/Clover/WeChat/Alipay Worlds should be generated from canonical synthetic businesses: restaurant, salon, ecommerce store, service contractor, agency. This makes many future products testable with the same Harbor substrate.</p>
</li>
<li>
<p><strong>OpenAPI/MCP adapter factory</strong> — When Oracle discovers an official OpenAPI/CLI, automatically generate or install an agent-facing interface and update the opportunity’s H-level. Concrete shows the pattern; Heroku/Square show the end state.</p>
</li>
<li>
<p><strong>Artifact-family expansion</strong> — Once one product sells, the worker should create adjacent variants only after outcome evidence: one Odoo localization → related compliance module; one technical 3D object → parametric family; one mini-app → cross-platform port. This is where persistent worker knowledge should compound.</p>
</li>
</ol>

<p><strong>3. Craft commercial plugin:</strong> smallest clean experiment in true plugin-market revenue. Craft’s 20% commission, GitHub requirement and licensing system make outcomes easy to attribute.</p>
<p><strong>4. Odoo vertical module:</strong> test the persistent-maintainer thesis across annual ERP versions and one region/industry niche.</p>
<p><strong>5. WeChat→Alipay paired experiment:</strong> build one extremely narrow paid utility, then measure the marginal labor/cost to port it to the second mini-program ecosystem. This directly tests whether <code>CrossVenuePortingProcess</code> becomes a reusable Moltwork asset.</p>

Core Oracle conclusion
<p>This batch reinforces a useful filter: the best market is not necessarily the biggest marketplace. It is the market where <strong>economic callability × repeatable evaluation × recurring maintenance value</strong> is highest.</p>
<p>Square and Heroku lead this run because the product, test environment, operations and billing are increasingly machine-operable. Craft/Odoo/CMS stores are attractive because the artifacts are deterministic and buyers pay for maintenance. Mini Programs are strategically huge because a successful worker/process may transfer across multiple super-app ecosystems.</p>
